02

The shared spine — anatomy of one send

Every payment from every adapter walks the same nine stages. Steps 1–4 and 7–9 are inherited from gec_bank and the payroll engine; a bank adapter only rewrites how it transmits and how it reads the answer (and adds its own proof machinery). Click a stage to see the shared guarantee and what each bank does there.

→ → → → → → → →
stage 01 · shared by gec_payroll_bank + gec_bank

Pre-flight runs before a pay run

The payroll engine asks the channel one question: “can I use you?” — and the core checks are sealed: banks may only append their own.

The shared guarantee

  • _gec_bank_config_errors() = core checks + _gec_bank_extra_config_errors(). Banks cannot remove a core check.
  • Channel must be an outbound line on a bank journal, with a reconcilable Outstanding Payments account that is not the journal default and not a cash/credit-card account.
  • api channels additionally need the journal IBAN — otherwise payments can never wait for the statement.
  • Per-recipient checks run via _gec_bank_check(kind, lines); everything is joined into one error.
TBC
  • Connection must exist and not be blocked.
  • Treasury recipients: exactly 9-digit code, GEL only.
  • Non-Georgian IBANs are refused.
BOG
  • Connection present and unblocked.
  • No State Treasury recipients at all.
  • Georgian IBAN (GE…, 22 chars) + known BIC per account.
Basis
  • Connection + channel setup checks.
  • Recipient needs a BIC (treasury partners skipped).
  • GEL + a non-empty memo for national transfers.
Trap: one bad channel refuses the whole pay run. Nothing is posted before the check passes, so there is nothing to clean up.
stage 02 · shared · account.payment

Fences both directions

A payment may not leave twice, and a payment the bank may hold may not be silently undone.

The shared guarantee

  • _gec_bank_check_sendable() refuses drafts (no journal entry yet) and anything no longer Paid — already matched, rejected or cancelled. This is the double-payment fence.
  • _gec_bank_at_bank() blocks every undo path: payment reset-to-draft, cancel, delete, and the journal entry’s reset/cancel.
  • A bypass context key exists for exactly one core flow: un-matching a statement.
TBC at-bank states
  • sending, sent, confirmed, unknown
BOG at-bank states
  • sending, created, sent, confirmed, unknown
  • created counts too — BOG holds a document.
Basis at-bank states
  • sending, sent, unknown, not_in_report, confirmed
Why: the fences run from the buttons and the @api.ondelete hook, not from every write. A direct ORM write can still bypass them — scripts beware.
stage 03 · bank-specific · nothing reserved yet

Order checks every adapter

Each adapter gathers all the problems in one pass, so a refusal leaves zero trace: no request id, no state change, no bank call.

The shared pattern

  • Refuse before reserving. The claim in stage 04 is the last thing that writes.
  • Errors are accumulated, not raised one by one — the operator sees the full list at once.
  • The same checks run whether the payment came from the payment form or from Pay Salaries.
TBC · _tbc_check_order
  • amount > 0; journal IBAN present
  • treasury: GEL + 9-digit code
  • recipient account present
  • transfer type matches the IBAN bank code
  • foreign: beneficiary address/bank + SHA/OUR
BOG · order of refusals
  • own bank → last send unknown → failed → already sent → approval missing → not Paid → channel config
  • attachments are uploaded before anything is claimed
Basis · _check_before_send
  • recipient account + allow_out_payment
  • missing BIC; empty memo
  • non-GEL national/treasury
  • method setup (sealed core checks)
Basis subtlety: the send button posts a draft before checking. A refusal rolls that posting back — and the entry number quoted in the error is freed, so don’t go looking for it.
stage 04 · the heart of gec_bank

Durable claim one conditional UPDATE

Before any money moves, the payment is claimed with its request id and a “sending” state — written on its own cursor, outside the request’s transaction.

The shared guarantee

  • _reserve_send(): UPDATE … WHERE state NOT IN blocked with a 2 s lock timeout, on an independent cursor.
  • A crash cannot roll the request id back; a double-click finds no row to claim.
  • Only plain stored columns may be claimed (_durable_columns validates).
  • REPEATABLE READ rule: after a durable write, the same transaction must never UPDATE that row again — PostgreSQL refuses and Odoo re-runs the whole request, send included.
TBC · claimed fields
  • gec_bank_request_id: numeric string < 10⁹, reused across retries
  • gec_bank_state='sending'
  • blocked: sending/sent/confirmed/unknown
BOG · claimed fields
  • gec_bank_request_id (UUID) + bog_document_no ODOO<id>; the old bog_bulk_key cleared
  • gec_bank_state='sending'
  • blocked: sending/created/sent/confirmed/unknown
Basis · claimed fields
  • ClientInternalID / DocNum = payment id
  • basisbank_state='sending' + send date for every member (all-or-nothing claim)
  • blocked: awaiting_approval, failed, sending/sent/unknown/not_in_report/confirmed
The law: claim first, transmit second. Every adapter reserves before the POST, so a lost answer always has a request id to recover by — never a blind resend.
stage 05 · bank-specific · network

Transmit soft — an answer may never come

One HTTP call in soft mode: transport errors return a status instead of raising, so “no answer” is a first-class outcome, not an exception.

The shared pattern

  • Every call goes through the adapter’s _call(): token/ticket, request, redacted log row on its own cursor.
  • http_status = 0 means “no response”. Nobody auto-retries it.
  • TLS, token caching and retry rules live here; pay-run payloads do not.
TBC
  • POST transfers/single — one order per payment
  • 60 s timeout; batch = per-payment savepoint loop
  • bearer token, 401 → one re-auth retry
BOG
  • one document per payment, or one bulk POST for a batch (≤ 500, no per-line result)
  • 60 s money timeout; 5 req/s process-local throttle
  • 429 → one retry; 401 → one re-auth
Basis
  • op 7 single item, or package ops 4/5/6 (all-or-nothing) / op 7 mixed
  • 15 s timeout; Digipass OTP inside the body
  • ticket in body, refreshed per call; code 3 → one re-auth (report only)
Basis twist: the OTP dialog row is deleted before the send. If the send fails pre-claim, the rollback restores it — the OTP is not lost, but it is transient by design.
stage 06 · bank-specific · the most read code in each module

Read the answer accepted · refused · unknown

Every reply is parsed into exactly one of three meanings. The hard rule everywhere: ambiguous is never a failure.

The shared rule

  • Accepted → the bank holds the request; record its bank id.
  • Refused → a definite no; safe to fix and resend.
  • Unknown → no answer, 5xx, timeout, or “id already exists”. Never resend blindly — recover first.
  • _parse_json/_first_key handle arrays, bare integers and bare strings: never assume a dict.
TBC
  • 207 multi-status: succeeded[].transferId → sent
  • failed[] → failed; 4xx → failed
  • duplicate code → park unknown, then look it up
  • 0 / 5xx / no id → unknown
BOG
  • ResultCode 0 → created — ready to sign, not moved
  • warn 333/444/701 → awaiting_confirmation; 363 → failed
  • 702 (id exists) → unknown — “check before resending”
  • letters A/Z S/T P R/D/C arrive later
Basis
  • ErrorCode 0 → sent (package: accepted as a whole)
  • 2 / 3 → clean retry: OTP wrong / ticket stale
  • 999 → unknown; others → failed
  • op 7: per-item verdict keyed by ClientInternalID
Most expensive mix-up: BOG’s created and Basis’ “package accepted” mean the bank has the order — not that money left. TBC’s transferId is the closest to “sent”, and still not “paid”.
stage 07 · shared · past the ORM

Durable write & mirror

The result is written on its own cursor too, then mirrored onto core fields — and because that write bypassed the ORM, the batch recompute is scheduled by hand.

The shared guarantee

  • _durable_write() — independent cursor, lock fallback to a tracked ORM write (returns False, logged).
  • Results flow through _gec_bank_write_result(): only whitelisted columns (_gec_bank_result_columns), written through the guard; a state that keeps no approval clears it.
  • _gec_bank_mirror_vals(): held → is_sent = True; refused from Paid → state = 'rejected' and is_sent cleared.
  • _gec_bank_after_durable() re-schedules batch state and amount_residual recomputes.
  • A rejected payment keeps its journal entry — history is not unwound.
TBC · held means
  • sent, confirmed
  • result columns whitelisted in _gec_bank_result_columns (+ tbc_bank_status)
BOG · held means
  • created, sent, confirmed
  • batch and members written in one durable pass
Basis · held means
  • sent, confirmed
  • claim is all-or-nothing across the batch
Why after_durable exists: a normal ORM write triggers computes automatically. A durable write does not — forget this call and the batch silently shows the old state.
stage 08 · shared · survives the rollback

Log & notify

One log row per bank call, committed on its own cursor — so the evidence of a failure outlives the transaction that failed. Then one notification closes the dialog.

The shared guarantee

  • Row values: endpoint, http_status, error_message, redacted request/response payloads, duration_ms.
  • Secrets are redacted by exact key match against the bank’s sensitive-key set ([REDACTED]), with a text-regex fallback.
  • _gec_bank_notify() returns a display_notification action that also closes the send dialog; sticky unless success.
  • Nightly autovacuum per connection: rows older than log_retention_days (default 90; 0 = keep all) are deleted — except rows each bank protects.
TBC log
  • tbc.api.log; endpoints containing transfers are never vacuumed
BOG log
  • bog.api.log adds result_code, correlation_id, is_money_movement
  • money-movement rows are never vacuumed
Basis log
  • basisbank.api.log adds error_code
  • main/upload rows are never vacuumed
Forensics: the log row survives the very rollback that erased the payment change. When a send “did nothing”, the log is the only place that knows whether the bank was reached.
stage 09 · the only true finish line

Prove & reconcile statement = proof

The payment is only confirmed when the bank’s own record of the movement matches it. Reference text alone never counts.

The shared guarantee

  • _gec_bank_matches_payment(): money out (amount < 0) for the exact amount in the payment’s currency — otherwise no match, even with the right reference.
  • _gec_bank_reconcile_payment() matches the open Outstanding line as superuser; the batch and the bill follow.
  • Statement imports dedupe by unique_import_id, so re-running an import is safe.
  • Status polling can confirm, but only the statement reconciles.
TBC
  • status Finished/Completed → confirmed
  • statement movement paymentId = transfer id or request id
BOG
  • letters S/T → sent, P → confirmed
  • statement matched by document key + number
Basis
  • report matched by BankInternalID, else DocNum
  • 48 h check: flags not_in_report, never touches accounting
Why so strict? a reversal or a credit can carry the same reference text. Matching on direction + amount + the bank’s own id is what makes the confirmation trustworthy.

Law 1 · Own cursor

Claim, result, and log rows commit on independent cursors. A rollback cannot erase a request the bank already saw.

Law 2 · Never touch the claimed row again

REPEATABLE READ: one more ORM UPDATE in the same transaction makes PostgreSQL refuse and Odoo re-run the request — a double send.

Law 3 · Unknown ≠ failed

A timeout may mean the bank got it. Every adapter parks it, logs it, and recovers by the request id before anyone resends.

Signature moves

Five transfer types

own · internal · national · treasury · foreign map to BIS type names. Treasury needs GEL and a 9-digit code, and drops the credit account; foreign needs the SWIFT block + SHA/OUR.

Duplicate is not a failure

A duplicate answer parks the payment as unknown, then looks the transfer up by request id. Found → adopt transferId; not found keeps unknown.

Strict ambiguity separation

0 / 5xx / 207 without id → unknown, never auto-retried. Definite 4xx → failed. The two never mix.

Guarded recovery

Recover refuses a sending younger than 15 minutes. Only TBC’s own “not found” answer may reset to pending — the signal that a resend is safe.

Statement confirms by movement id

The imported movement carries paymentId; the adapter matches it against transfer id or request id (the docs don’t say which it echoes) plus the debit amount.

Balance snapshots

tbc.statement stores opening/closing balances and credit/debit sums — live upsert every 2 h (inactive) plus period rows. Informational only.

Recovery moves

No answer / timeout

Refresh after the fact, or Recover: GET by request id. 15-minute guard on sending.

“Duplicate” answer

Automatic lookup — never raises, never resends. If the lookup misses, the payment stays unknown.

Definite refusal

failed / Odoo Rejected, entry kept, approval cleared. Fix the data, reset, send again.

Never proven

Refresh Status, import statements, or Confirm Manually. Only the statement reconciles.

Payroll note: Pay Salaries ends at the sealed batch — TBC gets no automatic send. The channel hook stamps treasury recipients (treasury + 9-digit code) and refuses any non-Georgian IBAN before the run starts.

Signature moves

“Created” is not “sent”

ResultCode 0 means BOG accepted the document for signing. Only status letters or the statement move a payment past created.

Warn codes + Create Anyway

333/444/701 inside HTTP 200 mean the document was not created. “Create Anyway” resends the same UniqueId; a real duplicate answers 702 instead of paying twice. 363 (duplicate) is the one warn that goes straight to failed.

CheckUniqueId

Every document asks BOG to enforce id uniqueness. A resend of an id BOG already holds answers 702 → the payment parks at unknown.

Bulk reality

The bulk POST returns a bare integer key with zero per-line results. The package is a container: a signed package can hide a rejected line → the batch ends partial. Package letters invert the document ones (P = To be Signed!).

Recover in today’s activities

Status lookup needs the UniqueKey, so a lost answer is recovered by DocumentNo in today’s activities (quota 800/day) → then the key + status refresh.

Name match score

bog_match_percent against the configured threshold (default 80) records how well the beneficiary name matched. gec_bank_confirmed_source records what confirmed it.

Recovery moves

No answer / timeout

unknown; Recover searches today’s activities by DocumentNo. Batch members recover individually.

Bank warning (333/444/701)

awaiting_confirmation. Create Anyway re-sends the same UniqueId; Reset to Pending keeps it so a future retry can only hit 702, never double-pay.

Duplicate (363 / 702)

363 → failed, Create Anyway is never offered. 702 → unknown: BOG already holds the id — recover, don’t recreate.

Never proven

Refresh Status (letters S/T → sent, P → confirmed) or import the statement. Confirm Manually sets status only — the statement reconciles.

Payroll note: the BOG channel refuses State Treasury recipients outright, so a mixed payroll fails fast instead of half-paying through the wrong bank. Salaries are flagged IsSalary and dispatched as BULK (≤ 10,000) or MT103.

The seven handoff states what the watchdog speaks

prepared

Sealed, not sent (or waiting for approval). Alerts after 48 h.

pending

At the bank but not yet accepted — e.g. BOG created. Alerts after 48 h.

transmitted

Bank holds it, result pending. Silent, never urgent.

Every member proven. The only state the watchdog forgets.

Some members confirmed/failed — merged from payments. Urgent.

All members failed. Urgent.

Timeout / no answer / unknown. Urgent — resync, never reverse.

One failed member → partial; all failed → failed; all confirmed → confirmed.

The watchdog every 4 hours

What it does. Scans unacknowledged payroll batches, asks each channel for its handoff state, and opens a “Payroll batch not confirmed by the bank” activity on the creator when something is wrong. It dedups by the last state it notified, and terminal states are recorded silently.

Timing. Urgent states (partial, failed, uncertain) alert immediately. Calm states (prepared, pending) get 48 hours measured from batch creation. Batches created with “Record only” on a manual channel are excluded forever.

Known rough edges (from the map):
  • Pay Salaries opens the batch list; each batch is sent from its own form — with several batches, nothing is sent until each is opened and its Send pressed.
  • The watchdog has no age cutoff: any unacknowledged batch that never reaches confirmed keeps being re-inspected (it only stops re-notifying the same state).
  • Basis ≤ 10,000 / TBC / BOG all leave sending to a human — an unattended payroll will sit at prepared until it shows up in the activity.
07gec_bank

The contract every bank signs

gec_bank ships no screen: its product is this contract — seven abstract mixins, the shared transfer flow on account.payment, and two families of hooks. A bank adapter inherits the mixins, opts its method code into the flow, answers the hooks, and gets every behaviour on this page for free.

1 · Durable send claim

_reserve_send writes the request id + sending state in one conditional UPDATE on its own cursor, before any money moves. Only plain stored columns; no fallback.

2 · Durable outcome write

_durable_write records the bank answer past the ORM; _gec_bank_write_result whitelists the columns, clears a spent approval, and mirrors is_sent / rejected; _gec_bank_after_durable schedules the batch recompute.

3 · Audit log row

One row per call on its own cursor, payloads redacted against the bank’s sensitive keys, duration measured. The row survives the rollback it describes.

4 · Response parsing

_parse_json + _first_key: empty → None; never assume a dict. A missed key degrades one field, never corrupts a statement.

5 · Field guard

gec.bank.guard.mixin: the transfer fields are refused to every direct write without the in-process token — forms, imports and RPC cannot forge an approval or undo a sent state.

6 · OAuth cache

gec.bank.oauth.mixin: the bearer token cached with a 60-second margin, sudo-read, written only by the service methods that cannot be called over RPC.

7 · Channel checks

_gec_bank_config_errors = sealed core checks + _gec_bank_extra_config_errors. Banks only add. One joined refusal before a pay run.

8 · Payment & batch values

_gec_bank_payment_vals decorates one created payment; _gec_bank_batch_vals merges into the batch. Booking fields and caller-owned keys are refused.

9 · Handoff state

_gec_bank_handoff_state answers with one of 7 states; the merge helper folds per-payment answers. No I/O, ever.

10 · Channel kind

_gec_bank_channel_kind (api/file/manual) and the opt-in _gec_bank_transfer_flow. Only the bank override may say api.

11 · Recipient account

_gec_bank_recipient_account finds the partner’s account at the paying bank by 8-char BIC; the register key routes the payment there.

12 · Approval team

Approver + delegates + company, stored name, and the constraint that the primary approver cannot be a delegate. Banks supply the table.

The six controls what is refused, and when

Mapped bank outcome

held → is_sent; rejected from Paid → state=rejected + clear is_sent; executed changes nothing.

At-bank fence

Reset/cancel/delete of a payment or its entry is refused while the bank holds it or may hold it.

Sendable fence

Drafts and no-longer-Paid payments are refused before any bank call — the double-payment guard.

Approver rule

The primary approver may not sit in the delegates list; an approver who may no longer approve voids what they approved.

Channel config fences

Outbound, bank journal, reconcilable Outstanding account ≠ journal default, not cash type, and an IBAN for api channels.

Statement verification

Money out, exact amount in the payment’s currency; reconcile the open Outstanding line. Reference alone never matches.

The hooks what a bank adapter implements

Channel hooks (on account.payment.method.line, called by Pay Salaries and the checks):

_gec_bank_transfer_flow()
the opt-in · per method code

True for the bank’s own code on a journal that belongs to it. Only opted-in channels run the shared transfer flow.

_gec_bank_channel_kind()
called by the wizard + checks · guard on self.code first

Answers api, file or manual. Base: file if the method generates files, else manual. Only a bank may claim api.

_gec_bank_extra_config_errors()
folded into the sealed config check

Appends blocking messages (connection missing/blocked, credentials…). Core checks cannot be removed, only added to.

_gec_bank_check(kind, lines)
called before a pay run · accumulator

Per-recipient and per-kind refusals: treasury codes, IBAN country, BIC, memo, GEL rules. Returns a list; the engine joins them.

_gec_bank_payment_vals(kind, payment)
after each payment is created + reconciled

Decorates the payment (transfer type, salary flag, treasury code). May not touch booking fields or the method line.

_gec_bank_batch_vals(kind)
merged into the batch create vals

Adds batch-level fields (salary flag, endpoint…). The caller-owned keys are reserved — an override raises and the run rolls back.

_gec_bank_handoff_state(batch)
watchdog · no network I/O allowed

One of the 7 handoff states, from the payments or the batch. The merge helper folds per-payment states; a batch is confirmed only when every payment is.

Transfer-flow hooks (on account.payment, answered per method code by TBC and BOG):

_gec_bank_label_for(code) · _gec_bank_connection_record()
messages · configuration

The bank’s translated name and its connection record (sudo). Without a usable connection there is no approver rule to check.

_gec_bank_send_one() · _gec_bank_refresh_one()
the network steps

Send one payment (returns True or a notification) and refresh its status from the bank. Everything else in the send is shared.

_gec_bank_new_request_vals() · _gec_bank_check_instructions()
the claim · the refusal

What the durable claim writes (the request id, minted once and reused) and what the bank is documented to reject, checked before anything is claimed.

_gec_bank_payload_fields() · _gec_bank_result_columns()
approval voiding · result whitelist

The fields the instructions are built from (a change voids the approval) and the columns a bank answer may write durably.

_gec_bank_state_groups() · _gec_bank_protected_fields() · _gec_bank_at_bank()
meaning · guard · fences

Which groups a bank’s extra states belong to (BOG: created → at_bank/held/open), which fields only bank flows write, and when the bank holds the payment.

Writing a new bank in five moves: inherit the mixins (guard, service, sendable, approval, connection — OAuth if it’s a bearer bank) → set _gec_bank_log_model + _gec_bank_sensitive_keys and add your result columns → opt your method code in (_gec_bank_transfer_flow) and answer the transfer-flow hooks with your request id → wire your journal by BIC and your Send button to _gec_bank_send_transfers → add your own states and place them in _gec_bank_state_groups. The spine (claim, write, log, fences, mirror, handoff, statements) comes for free.
08

Gotchas, by the symptom

The questions developers actually ask in the first hour, distilled from the 98 Q&A entries in the five maps. Symptom → cause → fix.

Shared gec_bank

“These fields are set by the bank integration and cannot be changed directly.”›

Cause: the guard mixin refused a direct write of a protected field (bank state, request id, reference, approver…) — readonly only guides the web client; the guard enforces it over forms, imports and RPC.

Fix: don’t fight it. The state changes through the bank’s buttons (Send, Recover, Resync, Reset); bank flows write through their own token-guarded path.

The Outstanding Payments account stays empty on a bank channel.›

Cause: the fill runs at create time only, and only for channels whose kind is api.

Fix: set the account by hand, or re-create the payment method line on an api channel.

“This payment is being changed by another operation. Reload it and send again.”›

Cause: the durable claim hit its 2-second lock timeout — another transaction is editing the row.

Fix: just reload and send again. Nothing was claimed, no money was touched.

“These payments are at the bank, or may be…” on reset / cancel / delete.›

Cause: the at-bank fence — the payment is in a state where the bank holds it or the last send was never answered.

Fix: don’t force it. Use the adapter’s recovery (Recover / Resync), then undo once the payment is proven untouched.

The batch still shows the old state after the bank answered.›

Cause: the durable write bypasses the ORM, so the batch recompute did not run.

Fix: the adapter must call _gec_bank_after_durable(vals); it re-schedules batch state and amount_residual.

API logs grow forever / never get cleaned.›

Cause: retention 0 skips the connection, and with no override the base vacuum domain deletes nothing (it is a whitelist of deletable rows).

Fix: set log_retention_days (default 90) and make sure the bank’s _gec_bank_log_vacuum_domain selects the routine rows it wants removed.

TBC tbc_bank

The Send button is missing on a payment.›

Cause: the form only shows Send for gec_bank_code = 'tbc_transfer' + Odoo state paid + gec_bank_state in pending / approved.

Fix: for other states use Recover / Refresh / Confirm Manually (each has its own visibility rule). If the payment is not a TBC transfer at all, check the journal BIC.

A TBC bank journal is not flagged as TBC.›

Cause: the BIC must start with TBCBGE22 (11-char BIC is accepted — the first 8 decide).

Fix: correct bank_bic; the connection itself is resolved per company, not per journal.

“Send” refuses with no bank call — the log is empty.›

Cause: _tbc_check_order refused before the claim: amount, journal IBAN, treasury GEL + 9-digit code, recipient account, transfer type vs IBAN bank, SWIFT fields + SHA/OUR.

Fix: the error lists every problem at once; fix them all and resend. Nothing was reserved.

An unknown payment won’t resend.›

Cause: the claim blocks unknown on purpose — the previous attempt may have reached TBC.

Fix: Recover. Only TBC’s own “not found” answer may reset it to pending as a safe-to-resend signal; the 15-minute guard applies while it is still sending.

A memo edit silently killed the approval.›

Cause: any write touching TBC_ORDER_FIELDS revokes an awaiting/approved transfer back to pending so changed instructions can’t ride the old approval.

Fix: re-submit and re-approve. The maker can’t be the checker unless the connection allows self-approval.

BOG bog_bank

The payment is “confirmed” but still shows unreconciled.›

Cause: status refresh, Recover and Confirm Manually change gec_bank_state only. Only the statement reconciles.

Fix: import the statement, or activate the daily statement sync cron for active connections.

An unknown document blocks every retry.›

Cause: ambiguous answers are never resent — the sendable filter skips unknown, batch members included.

Fix: Recover by DocumentNo in today’s activities; the found DocKey restores created and the status can refresh.

ResultCode 333 (insufficient working balance): was it sent or not?›

Not created. Warn codes 333/444/701 inside HTTP 200 mean BOG did not create the document. The payment waits at awaiting_confirmation.

Fix: settle the cause, then Create Anyway — it re-sends the same UniqueId. If BOG secretly holds it, the answer is 702 → unknown, never a double payment.

A bulk batch says package signed, but one salary is missing.›

Cause: the bulk POST returns no per-line result. A signed package can contain a rejected line; the batch becomes partial only after the line statuses are read.

Fix: Refresh Batch Status (or the batch poll cron) — the rejected member turns failed with its reject code, the rest continue.

Recover can’t find a document from yesterday.›

Cause: the recovery endpoint is today’s activities only (quota 800/day/account).

Fix: run Recover the same day, or confirm through the statement import; a lost document still has its API log row.

Basis basis_bank

The journal is at Basis but Odoo doesn’t treat it as a Basis journal.›

Cause: Basis needs both: BIC CBASGE22 and a connection on the company or a parent company.

Fix: create the connection (journals refresh automatically) or correct the BIC.

An unknown batch refuses reset and resend.›

Cause: the claim treats sending, sent, unknown and not_in_report as blocked — a blind resend could duplicate a package.

Fix: use the batch Resync wizard; batch reset is refused while any member is sending/sent/unknown.

“Not in Bank Report” — why didn’t it reverse the payment?›

By design. After 48 hours without a report hit the hourly check only flags: state, chatter note, and a TODO activity. The bank may still book the transfer, so accounting is untouched.

Fix: Resync later, or Reset to Pending — which re-reads the report before doing anything.

Old posted payments suddenly turned Pending.›

Cause: creating a connection cascades is_basisbank and recomputes states — including months-old outbound payments on those journals (KNOWN_ISSUES.md A3, a double-payment path).

Fix: review old payments after creating a connection; only drafts should ever be sent. The same cascade fires when the connection moves between companies.

One transfer in an op-7 batch was refused — what happened to the rest?›

Op 7 answers per item: only the refused payment goes failed (entry kept), the accepted ones proceed, and the batch can still reach done. Packages (ops 4/5/6) are all-or-nothing — error 11 fails the whole package.

Payroll bridge gec_payroll_bank

The “Pay Salaries” button is missing.›

Cause: gec_payroll_can_pay is false (no validated slip with net wage > 0) or you are not in Payroll Administrator. The run entry point is the kanban card action.

Fix: confirm the slips / check the group.

“The amounts changed while you were working — nothing was created.”›

Cause: between the wizard’s residual snapshot and the row lock, another transaction settled a line (a 50.00 partial payment is enough).

Fix: reopen the wizard; the rollback means nothing was written. A retry takes a fresh snapshot — the partial guard then refuses instead.

“You cannot set partner_bank_id on an already posted payment.”›

Cause: a channel hook returned a booking field (or the method line) in _gec_bank_payment_vals. Routing must be decided before creation.

Fix: move that logic earlier; hooks may only add their own decoration fields.

“The bank hook tried to re-route a posted payment” — the whole run rolled back.›

Cause: the hook returned a protected field (partner_bank_id, payment_method_line_id) or a reserved batch key (journal_id, payment_ids, gec_payroll_*…).

Fix: pure decoration only. The rollback is deliberate: payment, reconciliation, paid state, routing and batch are all restored.

A batch cannot be deleted or edited.›

Sealed by design: eight routing fields are immutable behind an in-process token that never crosses RPC; membership is locked and an envelope constraint holds the batch together.

Recovery path: reset a rejected payment to draft → cancel it → “Mark Unpaid” → pay again. The rejected payment stays as history.

Activity: “Payroll batch not confirmed by the bank.”›

Cause: the 4-hourly watchdog read the handoff state: partial/failed/uncertain alert immediately; prepared/pending after 48 hours. Manual-ack batches are excluded.

Fix: check with the bank / use the adapter recovery — never resend blindly.

Vocabulary

Claim / durable writea write committed on its own cursor, outside the transaction, so a rollback cannot undo it.
REPEATABLE READ ruleafter such a write, the same transaction must never UPDATE the row again — PostgreSQL refuses and Odoo re-runs the request.
At-bankthe payment is in a state where the bank holds it or may hold it; all undo paths are fenced.
Unknownno usable answer (timeout / 5xx / ambiguous). Recover by id; never blind-resend.
Guard / write tokenthe in-process Python object a bank flow must hold to write protected fields; it cannot cross RPC or an import.
Handoff statethe 7-value vocabulary the payroll watchdog reads from the bank channel.
Sealed batcha payroll batch whose routing fields are immutable behind an in-process token; members cannot join or leave.
Soft calla bank call that returns the outcome (including “no response”) instead of raising.
